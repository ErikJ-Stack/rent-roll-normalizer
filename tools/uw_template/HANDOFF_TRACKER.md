# UW Template Handoff Tracker

Running log of changes Claude Code has made (or proposed) that require operator
action in the **ALF UW Template** (authored externally in Excel via Cowork).
Newest at top.

This file is the **index**. Each row links to a dated handoff brief in
[`handoffs/`](handoffs/) with the full detail. New handoffs are created from
[`HANDOFF_TEMPLATE.md`](HANDOFF_TEMPLATE.md).

## Why this exists

The ALF UW Template (`Sample Files/ALF_UW_Template_v4.xlsx`, gitignored) is a
downstream-consumer artifact. Per the Track 4 ownership split, **the template
is authored externally** (Cowork → Excel by the operator); Claude Code owns the
**registry** ([`registry.json`](registry.json)) and the **writer**
([`uw_template_writer.py`](../../uw_template_writer.py)).

When Claude Code work surfaces a template-side change — a missing column, a
needed new row, a styling decision, a structural addition — the chat that
surfaced it produces a handoff brief here instead of editing the template
itself. The operator then picks up the brief and authors the change in Excel,
optionally roundtripping via Cowork.

## When to create a new handoff

Trigger conditions (any one is enough):

- A registry entry gains `gap_target` status (UW Output produces a value with
  no template row to receive it).
- A registry entry's target cell changes (e.g. a row shifts, or a concept
  moves from `'T-12 Analysis'!N62` → `'T-12 Analysis'!N106`).
- A new substrate column or row needs a corresponding template-side surface
  (e.g. substrate v0.2.13 Preleased exposure → template-side Preleased Date
  column).
- A writer scope decision needs operator input that depends on template
  structure (e.g. "should writer overwrite the hardcoded `Apr-25..Mar-26`
  monthly headers, or leave them?").
- A new template version is being prepared (e.g. v4 → v5).

If a Claude Code change only touches the **writer** or **registry** without
implying any template-side action, no handoff is needed — the change lands in
`registry.json` + the regenerated MAPPING_TRACKER artifacts and that's enough.

## Status legend

- **Pending operator** — handoff produced; waiting for the template to be updated in Excel.
- **In progress** — operator has started authoring; not yet dropped back in.
- **Applied** — new template file present at `Sample Files/ALF_UW_Template_v5.xlsx` (or whichever version); registry not yet updated to point at it.
- **Verified** — registry updated; `populate_uw_template(..., template_version='v5')` smoke-tested; handoff is closed.

When a handoff hits **Verified**, leave the row in place (audit trail) and
update its Status. Newer handoffs continue to slot in at the top.

## Mapping updates

Mapping updates ride **inline in each handoff** — they are almost always
coupled to template-side changes. The authoritative full-state artifacts are
unchanged and still regenerated by
[`build_mapping_artifacts.py`](build_mapping_artifacts.py):

- [`registry.json`](registry.json) — source of truth.
- [`MAPPING_TRACKER.md`](MAPPING_TRACKER.md) — human-readable tracker.
- [`mapping_tracker.csv`](mapping_tracker.csv) — diffable.
- [`mapping_mindmap.html`](mapping_mindmap.html) — interactive.

Re-run `python tools/uw_template/build_mapping_artifacts.py` after applying
the registry-side changes a handoff prescribes.
